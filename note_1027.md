To take this document from a "great framework" to a "production-ready standard," I recommend focusing on **Gatekeeping, Hybridity, and Verification.**

The current document describes the *path* very well, but it could be strengthened by defining the *checkpoints* and the *exceptions*.

Here are 5 specific areas to improve the document and the workflows:

### 1. Explicit "Human-in-the-Loop" (HITL) Gatekeeping
Currently, the flow is: `Analysis -> ADR -> Architecture -> Memory -> Implementation`. 
**The Risk:** If the AI's "Analysis" or "ADR" is flawed, the "Coder" will perfectly implement a wrong solution.

*   **The Fix:** Insert a mandatory **"Human Review"** gate after the **ADR/Architecture** phase.
*   **Workflow Update:** 
    *   *Current:* `ADR作成 (Cherry Studio Analyst) -> アーキテクチャ設計`
    *   *Proposed:* `ADR作成 (Cherry Studio Analyst) -> **[Human Review & Approval]** -> アーキテクチャ設計`
*   **Why:** This ensures the "Thinking" is correct before any "Building" (and token spending) occurs.

### 2. The "Hybrid" Workflow (The Reality of Software)
Most real-world tasks are neither 100% Greenfield nor 100% Brownfield. For example: *"Add a new feature (Greenfield) that requires refactoring the existing database schema (Brownfield)."*

*   **The Fix:** Add a **"Hybrid"** flow or a "Complexity Assessment" step at the beginning of the Analysis phase.
*   **Workflow Update:** Add a step: **"Impact & Scope Assessment"** to determine if the task requires a Greenfield (Design-first) or Brownfield (Analysis-first) approach.
*   **Why:** This prevents the team from using the wrong workflow for complex, multi-faceted tasks.

### 3. The "Verification" Phase (Closing the Loop)
The current workflow ends at "Implementation." In a professional standard, the workflow shouldn't end until the code is verified.

*   **The Fix:** Add a **"Verification & Validation"** phase at the end of both flows.
*   **Workflow Update:** 
    *   `実装 (OpenCode Coder) -> **検証 (Verification)** -> 共通メモリ更新 (Final Review)`
*   **Verification includes:**
    *   **Unit/Integration Tests:** Did the Coder write tests?
    *   **Regression Check:** Did the Brownfield change break existing features?
    *   **Style Check:** Does the code match the project's standards?

### 4. Memory Lifecycle Management (SSOT Maintenance)
The document mentions the **Shared Memory** as the SSOT, but it doesn't say how to *clean* it. Over time, the memory can become cluttered with "Draft" ideas that were rejected.

*   **The Fix:** Define a **"Memory Lifecycle"** in Section 6.1.
*   **Proposed Addition:**
    *   **Draft/Intermediate:** `.opencode/shared/` (Temporary, deleted after implementation).
    *   **Permanent/ADR:** `docs/architecture/` (The "Source of Truth").
    *   **Action:** "Every completed task must result in a 'Cleanup' step where intermediate analysis is either promoted to an ADR or discarded."

### 5. Complexity Tiers (Efficiency)
Not every task needs a full ADR and a 5-perspective analysis. If you need a full workflow to change a button color, the process becomes a bottleneck.

*   **The Fix:** Introduce **Complexity Tiers** (e.g., Tiers 1, 2, and 3).
    *   **Tier 1 (Minor):** Simple bug fixes, typos, style changes. (Skip ADR, go straight to Coder).
    *   **Tier 2 (Standard):** New features, refactors. (Full standard workflow).
    *   **Tier 3 (Architectural):** Database changes, new modules, security overhauls. (Enhanced Analyst involvement).
