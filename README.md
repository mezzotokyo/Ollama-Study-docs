# AI共創型開発ワークフロー：思考のパートナーとしてのLLM

## Preface：AIを「道具」から「思考のパートナー」へ

AI（LLM）を単なる「コード生成ツール」として使うだけでは、複雑なシステムの設計や、長期的なメンテナンスが必要なプロダクション環境での開発には限界があります。

本リポジトリは、LLMを単なる「道具」ではなく、**「思考のパートナー」**として開発プロセスに深く組み込むための指針（Development Standard）を提示します。

私たちは、AIとの共創を以下の**「共創の役割分担」**に分解し、それぞれの役割を最適化することで、より高度な開発を実現します。

- **Cherry Studio / Analyst（思考）**: システムを理解し、**「考える」**場所。要求分析、ADR作成、アーキテクチャ設計を担当。
- **OpenCode Analyst（理解）**: 既存の資産を読み取り、**「理解する」**場所。コード読解、リファクタリング分析、技術的負債の調査を担当。
- **OpenCode Coder（実装）**: 100%の実装を**「作る」**場所。テスト生成、修正、コード変換を担当。
- **OpenCode Auditor（検証）**: 実装がADRに適合しているか、セキュリティ・回帰・副作用に問題がないかを検証し、**「保証する」**場所。
- **共通メモリ（記憶）**: 全ての知見を統合し、**「記憶する」**共通の知見。

> **Note:** 本リポジトリのコンテンツは、すべて本リポジトリで紹介している手法とツールを用いて、人間とAIの共創によって制作されました。

## Abstract：共創のフレームワーク

本リポジトリは、AIとの共創を「職人芸」から「構造化されたプロセス」へと昇華させるためのフレームワークを提供します。

主な柱となるのは、以下の3つの要素です。

1.  **開発標準（Development Standards）**: 開発の「ルール」を定義。
2.  **モデル構成（Model Configuration）**: 役割ごとのモデル選定やパラメータ設定.



3.  **実践Tips（Pro-tips）**: 共創の質を向上させるための実践的な知見。

## Quick Start: Your First Development Session

本リポジトリをすぐに使い始めるためのガイドです。分析（Cherry Studio）と実装・検証（OpenCode）を分けて進めます。

| フェーズ | ツール | ペルソナ（モデル） | 成果物 |
|---|---|---|---|
| 1. 分析 | Cherry Studio | Analyst（Ethical Architect / `ta:architect`） | 要件分析・ADR |
| 2. 承認 | 人間 | — | 承認済み ADR |
| 3. 実装 | OpenCode | Coder（Expert Engineer / `ta:engineer`） | コード・テスト |
| 4. 検証 | OpenCode | Auditor（Technical Auditor / `ta:auditor`） | Pass/Fail・指摘 |

### ステップ 1: 分析 — Cherry Studio / Analyst（Ethical Architect）

Cherry Studio を開き、新しい Session を作成し、ペルソナ設定で「Analyst（Ethical Architect）」を選択します。このペルソナは、5 つの視点（Functional, UX, Business, Org, Social）から要件を分析し、ADR（設計方針）を生成する思考のパートナーです。

日本語または英語で、以下の形式で要件を入力します：

```
要件：[何を作りたいか]

- **Functional:** [機能の仕様]
- **UX:** [ユーザー体験の要件]
- **Business:** [優先度や納期など]
- **Org:** [技術制約や既存システムとの統合]
- **Social:** [プライバシーや倫理的な配慮]
```

**例：**

```
要件：ユーザーログイン機能を作成したい。

- **Functional:** ユーザー名とパスワードでログインできる。エラーメッセージを表示する。
- **UX:** レスポンシブデザインで、モバイルでも使いやすい。
- **Business:** 優先度 High。来週金曜日まで納期。
- **Org:** 既存の認証システムと統合する。セキュリティ要件を満たす。
- **Social:** パスワードは暗号化して保存する。GDPR に準拠する。
```

### ステップ 2: 承認 — 人間によるレビュー

生成された ADR を確認し、承認します。実装に進む前に設計を確定させる Human-in-the-Loop（HITL）ゲートです。設計変更が必要な場合は、ステップ 1 に戻って ADR を修正します。

### ステップ 3: 実装 — OpenCode / Coder（Expert Engineer）

承認済み ADR をもとに、OpenCode の `ta:engineer` で実装とテストを生成します。ADR から逸脱する必要が出た場合は実装を止め、ステップ 1 の再分析に戻します。

### ステップ 4: 検証 — OpenCode / Auditor（Technical Auditor）

OpenCode の `ta:auditor` で、実装が ADR に適合しているか、セキュリティ・回帰・副作用に問題がないかを検証します。Pass/Fail と修正点を確認し、必要ならステップ 3 に戻します。

完了！承認済み ADR に基づく実装・テストと、検証結果が揃います。

## 5つの視点（The 5 Perspectives of Analysis）

AIとの共創において、最も重要なのは「分析の質」です。AIは強力な推論エンジンですが、正しいコンテキスト（文脈）が与えられない限り、一般的な回答しか返せません。

私たちは、あらゆる要求やタスクを以下の5つの視点で分解し、言語化することを推奨します。

1.  **Functional（機能）**: 「何ができるか？」
    *   システムの動作、入力、出力、およびユーザーが達成したい目的を定義します。
2.  **UX（ユーザー体験）**: 「誰が、どう使うか？」
    *   ユーザーの感情、操作の導線、アクセシビリティ、および「使いやすさ」の基準を定義します。
3.  **Business（ビジネス）**: 「なぜ、いつ、どれだけ作るか？」
    *   ビジネス価値、優先度、予算、納期、および「なぜ今これを作るのか」という背景を定義します。
4.  **Organizational（組織）**: 「技術スタック、セキュリティ、保守性」
    *   社内標準、既存の技術スタック、セキュリティ要件、および長期的なメンテナンス性を定義します。
5.  **Social（社会・倫理）**: 「プライバシー、アクセシビリティ、倫理」
    *   法令遵守、プライバシーへの配慮、および倫理的な影響を定義します。

**これらの視点が期待通りに実装されているかを検証する必要があります。詳細な検証基準については、[開発標準（Development Standards）](docs/standards/development-standard.md) を参照してください。**

## 共通メモリ（Common Memory）

AIとの共創において、**「記憶の断絶」**は最大の敵です。
私たちは、プロジェクトの「共通認識」を維持するための **Single Source of Truth (SSOT)** として、**共通メモリ**を定義します。

共通メモリは、単なるメモ帳ではなく、**「AIと人間が共有する唯一の正解」**です。
*   **アーキテクチャ設計やADR**: `docs/architecture/`
*   **開発中の動的な合意**: `.opencode/shared/`
*   **AIによる分析結果**: `docs/ai-findings/`

すべての開発ステップにおいて、常に最新の「共通メモリ」を参照し、合意事項を即座に反映させることで、一貫性のある開発を実現します。

## 開発フロー（Development Flow）

開発の性質に応じて、以下の2つのフローを使い分けます。

- **Greenfield**: 新規開発。**「要件」から「理想の姿」を構築する**フロー。
- **Brownfield**: 既存の資産をベースにした拡張。**「既存の制約」を深く理解する**フロー。

**※ 開発の各ステップにおいて、常に「共通メモリ」を更新・参照することが重要です。詳細なフローについては、[開発標準（Development Standards）] を参照してください。**

## Pro-tips（共創のコツ）

AIとの共創をより深く、スムーズに進めるための実践的な知見です。

### 言語の使い分け：思考の深化と効率の両立
*   **基本方針**: 日本語でのやり取りは、私たちの思考を整理し、ドキュメントを構築する際に非常に強力な武器になります。
*   **高度な推論への推奨**: 複雑なアーキテクチャの設計や、深い技術的負債の分析など、**「高度な推論」を必要とする場面では、英語でのやり取りを試すこと**をお勧めします。現在のLLMの特性上、英語でのやり取りの方が、より広範な学習データに基づいた深い洞察を引き出せる傾向があるためです。
*   **使い分けのコツ**: 「日本語で思考を整理し、複雑な分析の瞬間だけ英語に切り替える」というハイブリッドなアプローチが、現在の共創における最適解の一つです。

### ペルソナの設計：性格による振る舞いの制御
*   **役割を超えた「性格」の付与**: 単に「Analyst」や「Coder」という役割を与えるだけでなく、**「EthicalなAnalyst（倫理を重視する分析官）」**や**「SolidなReviewer（堅実なレビュー担当）」**といった、性格や価値観を定義することで、AIの回答の質と一貫性を調整できます。
*   **共創のコツ**: 複雑なタスクほど、AIに「誰として振る舞うか」を明確に定義することで、より意図に沿った、かつ深い洞察を得られるようになります。
